# @checkout/web — фронтенд магазина

React 19 + TypeScript + Vite, маршруты — react-router, серверное состояние — TanStack Query.
Типы и схемы берутся из `@checkout/contracts`; бэкенд не менялся.

## Запуск

Нужны Node.js 24 и npm 11 (`.nvmrc` в корне). Из корня репозитория:

```sh
npm ci
npm run dev        # API на http://localhost:4000 (терминал 1)
npm run dev:web    # фронтенд на http://localhost:5173 (терминал 2)
```

Сборка и просмотр собранного:

```sh
npm run build:web      # apps/web/dist
npm run preview:web    # http://localhost:4173
```

Адрес API задаётся переменной `VITE_API_URL` (см. `.env.example`), по умолчанию `http://localhost:4000`.
Если API запущен на другом порту — положите в `apps/web/.env.local` строку `VITE_API_URL=http://localhost:4100`.
`VITE_API_DELAY_MS=1000` там же добавит паузу перед каждым запросом, чтобы разглядеть состояния
загрузки и ожидания; по умолчанию паузы нет.
`npm run check` в корне теперь проверяет и форматирование фронтенда.

## Как устроена работа с API

```text
src/api/http.ts        request(spec) — единственное место отправки: адрес, заголовки, JSON-тело,
                       токен сессии, проверка статуса, 204, разбор конверта {data, meta, links},
                       ошибки сети/HTTP/разбора → ApiError {kind, status, code, fields, requestId}.
                       401 → гостевая сессия создаётся заново, запрос повторяется один раз.
src/api/session.ts     хранение токена (localStorage) и подписка на его смену.
src/api/endpoints.ts   вызовы API как данные: путь, метод, тело, Idempotency-Key. Никакой логики.
src/api/queries.ts     ключи кэша и queryOptions: staleTime, опрос статуса оплаты (refetchInterval
                       выключается на succeeded/failed/cancelled), расчёт как запрос с ключом
                       [версия корзины, доставка].
src/api/mutations.ts   изменение корзины, оформление (заказ + первая попытка оплаты), новая попытка,
                       выбор сценария; инвалидация кэша после каждого.
src/api/queryClient.ts общие правила: повтор только сети/5xx; CART_VERSION_CONFLICT → перечитать
                       корзину, QUOTE_EXPIRED → новый расчёт — для всех запросов и мутаций сразу.
src/lib/idempotency.ts ключ идемпотентности: один и тот же для повтора той же операции (двойное
                       нажатие, потеря ответа), новый — для новой попытки.
src/lib/validate.ts    проверка формы по схемам контракта (TypeBox Value.Errors) и приведение
                       error.fields из ответа API к тем же ключам полей.
src/lib/storage.ts     типизированное JSON-хранилище с кэшем и подпиской (useSyncExternalStore).
src/ui/                Button (pending = заблокирована + индикатор), Field/SelectField/RadioGroup
                       (label, aria-invalid, aria-describedby), Notice/ErrorNotice (сообщение +
                       «Повторить»), Async (загрузка/ошибка/данные для любого запроса), Stepper.
src/features/, pages/  компоненты получают готовые данные или разобранную ошибку и только рисуют.
```

Распределение обязанностей: транспорт (`http.ts`) ничего не знает о страницах; `endpoints.ts` —
о состоянии; `queries/mutations` — о вёрстке. Страница знает только ключи запросов и хуки.
Компонент не касается `Response`, не читает `error.code` для транспортных ошибок — только
состояния предметной области (`payment.status === 'failed'`, `order.status === 'paid'`).

Состояние оплаты не хранится на клиенте: страница заказа читает заказ и список попыток с сервера,
последняя попытка определяет, что показать (форму, ожидание, итог и кнопку новой попытки).
Поэтому перезагрузка страницы ничего не теряет, а «страница успеха» — это тот же заказ со статусом
`paid` из API. Локально хранятся только токен, черновик формы, id незавершённого заказа и ключи
идемпотентности.

## Разбор участка обработки данных

`useIndex(cart.items, byProductId)` в каталоге (`src/lib/index.ts`, `pages/CatalogPage.tsx`).

- **Частота.** Пересчитывается только когда сервер прислал новую корзину (после изменения
  количества или удаления), то есть один раз на действие пользователя; при перерисовках по другим
  причинам `useMemo` возвращает прежнюю `Map`.
- **Проходы.** Один проход по позициям корзины (`for…of`, без `map`/`filter`), одна `Map`.
  Дальше каждая карточка товара делает `inCart.get(id)` — O(1). Без индекса было бы
  `items.find(...)` в каждой карточке: O(товаров × позиций) на каждую перерисовку.
- **Память.** Одна `Map` на версию корзины и ничего больше: элементы не копируются, в неё кладутся
  ссылки на объекты из кэша TanStack Query. При обновлении корзины неизменившиеся позиции сохраняют
  ссылки (structural sharing), так что карточки с прежним `item` не перерисовываются.

Тот же принцип в других горячих местах: `validate` берёт первую ошибку каждого поля за один проход
итератора `Value.Errors` без промежуточных массивов; `trimmed` создаёт один объект за один проход;
`Stepper` не хранит копию значения — поле неуправляемое и пересоздаётся по `key` при смене
серверного значения.

## Принятые решения

- **Расчёт — это запрос.** `POST /api/quotes` описан как query с ключом
  `['quote', { cartVersion, delivery }]`: изменилась корзина или доставка — TanStack сам создаёт
  новый расчёт, старый не переиспользуется; адрес берётся с задержкой 400 мс, чтобы не считать на
  каждую букву. Конфликт версии обрабатывается в `queryClient` один раз для всех.
- **Оформление и первая попытка оплаты — одна мутация.** «Перейти к оплате» создаёт заказ и попытку,
  страница заказа сразу показывает платёжную форму. Если попытку создать не удалось, заказ всё равно
  создан — на его странице есть кнопка «Оплатить».
- **Идемпотентность.** Ключ привязан к «идентичности» операции (тело заказа; `orderId` + id
  предыдущей попытки для оплаты) и хранится в sessionStorage. Повтор после потери ответа и двойное
  нажатие отправляют тот же ключ и получают 200 с тем же объектом; новая попытка после отказа
  получает новый ключ.
- **Опрос.** `refetchInterval` у списка попыток включён только пока последняя `processing`;
  при уходе со страницы наблюдателей нет — опрос останавливается. Запоздавшие ответы не
  подменяют новые: у запроса с одним ключом одновременно идёт один fetch, отменённые игнорируются.
- **Валидация по контракту.** Правила (длины, `\S`, формат email, шаблон телефона) не дублируются:
  форма проверяется теми же TypeBox-схемами, что и сервер; тексты подписей — в одной таблице.
- **Отправка во время расчёта.** Если пользователь нажал «Перейти к оплате», пока расчёт ещё
  считается, кнопка переходит в ожидание и заказ создаётся, как только расчёт готов.

## Проверенные сценарии

Прогонялись Playwright-скриптом на dev-сервере (ширина 1280 и 390) и вручную:

1. Каталог → «В корзину» → +1 → корзина показывает 2 шт. и сумму, совпадающие с `GET /api/cart`
   → оформление, самовывоз, карта → форма → успешная карта → перезагрузка во время обработки →
   страница успеха с номером, товарами, доставкой и суммой; `GET /api/orders/{id}` даёт
   `paid / succeeded`.
2. Курьер (390 ₽ в расчёте) → карта с отказом → «Банк отклонил оплату» → «Оплатить снова» →
   «Отменить оплату» → «Оплата отменена» → «Оплатить снова» → успех. В API у заказа три попытки
   `succeeded, cancelled, failed`, заказ один.
3. Наличные при получении → «Заказ оформлен, оплата при получении», онлайн-оплата не создаётся,
   напоминание о незавершённом заказе исчезает.
4. Пустая форма → ошибки у полей, фокус на первом; неверные email/телефон, пункт не выбран →
   подписи под полями, заказ не отправлен; перезагрузка сохраняет введённое. Заполненное поле
   проверяется при потере фокуса (пустые при проходе табом не подсвечиваются), правка снимает
   ошибку; фокус при этом не перехватывается.
5. Корзина изменена в другой вкладке (через API) во время оформления → сообщение, состав и итог
   обновлены, форма сохранена → повторное нажатие создаёт заказ.
6. Двойное нажатие «Перейти к оплате» → один заказ.
7. Пустая корзина → оформление недоступно; товар без остатка — кнопка заблокирована; ввод 99 при
   остатке 5 → ограничено 5, «+» заблокирован; превышение через API даёт `INSUFFICIENT_STOCK` и
   показывается рядом с товаром.
8. Токен неизвестен API (сброс данных) → одна новая сессия, работа продолжается.
9. После ухода со страницы заказа запросов к `/payments` нет; возврат по баннеру показывает
   `paid` с сервера.
10. Ширина 390: горизонтальной прокрутки нет, поля и кнопки доступны.

## Известные недоработки

- Расчёт создаётся на сервере при каждом изменении доставки после задержки; неиспользованные
  расчёты живут 10 минут и не удаляются (API не предусматривает удаление).
- Корзина обновляется без оптимистичных изменений: каждое изменение количества — запрос и
  перечитывание корзины (итоги считает сервер).
- Черновик и токен не синхронизируются между вкладками (нет обработчика события `storage`).
- Пункт выдачи на странице заказа подписывается названием только если условия доставки уже
  загружены; иначе показывается его id.
- Автотесты в репозиторий не добавлены — сценарии выше проверялись внешним Playwright-скриптом.
